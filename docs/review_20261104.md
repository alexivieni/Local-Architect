# Code review: the Claude side, fleet, Logbook, costs, batches, fast lane (2026-11-04)

Scope: arch_cloud.py, arch_chat.py, arch_claudecode.py, arch_agents.py, arch_fleet.py, arch_learn.py, arch_costs.py, arch_batch.py,
arch_server.py (fast lane), arch_dataset.py (quality/dedupe/report), and the new endpoints in architect_hub.py.
Method: I read the code; I did not run it. **Verdict** says how sure each finding is: *confirmed* means the code path was read
end to end; *plausible* means it depends on library behaviour or call sites I did not trace all the way.
Line numbers are as of this review. architect_hub.py was being edited by another agent at the same time, so its line numbers will move;
the function or route is named too.

Severity: **High** = money lost past a cap, a stated rule broken (e.g. "self-tests never call Claude"), or training data corrupted.
**Medium** = a wrong result, a cap that does not hold, or data exposed under a realistic condition.
**Low** = robustness, memory, or a misleading message.

---

## High

### H1. Claude Code, fleets, Managed Agents and batches bypass the daily cap and never count towards it
- **Where:** arch_claudecode.py:299 `start`, arch_fleet.py:271 `launch`, arch_agents.py:20 `_client` / :77 `start`, arch_batch.py:65 `submit` / :101 `poll`;
  the cap itself is arch_cloud.py:486 (`spent_today() >= day_cap`), and it is written only from arch_cloud.py:600 `_add_spend`.
- **Scenario:** `limits.cloud_usd_per_day = 5`. The person launches two fleets of 16 agents with $1.25 each, which is $40. Nothing
  checks `spent_today()`, and the `total_cost_usd` from every `ResultMessage` is never added to `cloud_spend.json`. The day ends
  at $40 while the Settings card says "$0.00 of $5.00 today". Managed Agent sessions (including the nightly crew schedule) have no
  dollar limit at all. Batches add nothing to the daily total either, and accept any number of items with any `max_tokens`.
- **Fix:** add one helper, `arch_cloud.reserve(cfg, usd)`, that refuses when `spent_today() + usd > day_cap`. Call it in
  `cc.start(budget)`, in `fleet.launch(total_cap_usd)`, in `arch_agents.start` (a fixed per-session estimate) and in `batch.submit`
  (sum of `max_tokens` × output price × 0.5). Record what was actually spent with `_add_spend`: in `_drive` on `ResultMessage`, in
  `batch.poll` once results arrive, and for agents from the session's usage when it ends.

### H2. Claude Code starts without the `arch_cloud.allowed()` gate
- **Where:** arch_claudecode.py:299-305. The only checks are "SDK installed" and "`ANTHROPIC_API_KEY` set".
- **Scenario:** (a) Settings > Allow online features is **off**, but a key is set in the environment: the hub's Claude Code page and
  every fleet still launch paid agents. (b) A self-test or `eval` that reaches `cc.start` (any fleet test that forgets
  `starter=`) spends real money. That breaks "Self-tests never call Claude, whatever the settings say".
- **Fix:** at the top of `start`, add `ok, why = arch_cloud.allowed(core.load_config()); if not ok: raise RuntimeError(why)`.
  arch_agents `_client` (line 20) has the same gap for `ARCHITECT_EVAL`: replace its hand-written check with `allowed()`.

### H3. The daily spend file loses updates across processes, and on Windows silently drops writes
- **Where:** arch_cloud.py:358-379 `_add_spend`, :341 `_read_spend`, :351 `spent_today`.
- **Scenario:** The hub (Studio chat), `architect.py run` subprocesses (plan mode) and fleet local agents all write
  `cloud_spend.json`. Two problems follow:
  - `_SPEND_LOCK` only works within one process, so two processes do read-modify-write at the same moment and one call's cost is lost.
  - Every process uses the same temp name, `cloud_spend.json.tmp`. On Windows, `os.replace` raises `PermissionError` whenever any
    thread or process has the target open for reading. `spent_today()` is read on every `/api/arch/...` status poll, so this happens.
    The error is caught by `except OSError: pass`, so the call's cost is never recorded.

  Either way, the daily cap under-counts: the cap that is supposed to be the backstop leaks.
- **Fix:** use a per-process temp name (`f"{p}.{os.getpid()}.{thread id}.tmp"`, as `_cache_put` already does). Take a cross-process
  file lock around the read-modify-write (the msvcrt/fcntl pattern in arch_heavy.py). Retry `os.replace` about 5 times with a 50 ms
  sleep on `PermissionError`. If the write still fails, log it (stderr or trace) instead of `pass`.

### H4. Dataset dedupe treats different tasks as one, because prompts put the shared context first
- **Where:** arch_dataset.py `near_key` ("first 2000 characters of the user turn") and its use as the SFT key in `build`
  (`key = (role, near_key(user))`), and in the distill key.
- **Scenario:** CLAUDE.md requires prompts to be prefix-stable: instructions and project context first, the per-task part last. A
  coder prompt opens with thousands of characters of project context, so the first 2000 characters are often the same for every task
  in a project. With `dedupe=True` (the default), all of a role's samples from one project collapse into the single "best" one. The
  rest are counted as `duplicate` in REPORT.txt, so the person sees "dropped N: same task again" and believes it.
  *Plausible:* how much the context head varies depends on `rank_files` ordering. A whole-file test with two different goals over
  the same project would settle it.
- **Fix:** key on the per-task part, not the head. Either hash the whole normalised user turn, or hash the request/label taken from the
  call record, or use the last 2000 characters.

### H5. Calls in flight together all pass the per-run and per-day checks, and one call can overshoot by more than a dollar
- **Where:** arch_cloud.py:483-488 (the check), :511 (`max_tokens` up to 64000 for xhigh/max), and `ultra` :240/:269 (5 parallel calls).
- **Scenario:** the cap is $0.50 and $0.45 is already spent.
  - `ultra` starts 3 workers, then 2 skeptics, then the lead. Each call checks `_SPENT["usd"] >= cap` before any of them has added
    its cost, so all of them pass.
  - The lead at effort "max" on Opus may write 64000 output tokens, which is $1.28 for that one call alone.
  - `_SPENT["usd"] += usd` (line 598) is an unlocked read-modify-write from pool threads.
- **Fix:** before sending, reserve the worst case under `_SPEND_LOCK`: estimated input plus `max_tokens` × output price. Refuse if
  `spent + reserved + worst > cap`, and clamp `max_tokens` to what the remaining budget can pay for. Settle the actual cost after the
  reply arrives.

## Medium

### M1. Tokens Anthropic charged for are not counted when a call fails part-way, and fast mode retries a half-streamed reply
- **Where:** arch_cloud.py:584-593.
- **Scenario:**
  - A web-search reply pauses (`pause_turn`) and the resumed turn raises. The `pt/gt/cr/cw` from the first turn were charged by
    Anthropic but are never added to `_SPENT` or `_add_spend`.
  - In fast mode, *any* exception (a network drop after 3000 tokens had streamed, say) re-runs the whole call at normal speed. The
    text is sent to `sink`/`on_token` a second time, so the Studio bubble shows the answer twice and Engine traces hold duplicated
    output. The first attempt's cost is lost.
  - The retry also loses the role's effort: `_HERE.role` was already cleared, so it falls back to "high".
- **Fix:** add up what each turn cost as it finishes, and in the `except` path record it with `_add_spend`. Retry fast mode only when
  the stream failed *before* the first token, and only for a rate-limit or overload error. Pass `role` into the retry.

### M2. The hub's per-run cap is really a per-hub-process cap
- **Where:** arch_cloud.py:30 `_SPENT` (module-global, reset only by the self-tests) and arch_chat.py:177 `_reply`. Studio runs inside
  the hub process.
- **Scenario:** a few Ultracode answers in Studio add up to $0.50. From then on, every Claude chat in this hub fails with "Claude budget
  for this run is used up" until the hub restarts, even though no run is involved. arch_chat.py:226 also works out each message's cost
  as `spent()["usd"] - before`, so two projects chatting at once are each charged the other's spend.
- **Fix:** give the cap a scope. Use a thread-local or explicit `budget` object that the Engine owns per run (Studio: per message), and
  return each call's cost from `chat()`, which is already in `r["usd"]`, instead of subtracting global totals.

### M3. New GET endpoints skip the Host check (DNS rebinding can read transcripts)
- **Where:** architect_hub.py `AHandler.do_GET`: `/api/arch/claudecode` (~1490), `/subagents` (~1496), `/agents` (~1499), `/chat`
  (~1508), `/backlog` (~1511), `/report` (~1514), `/events` and `/events/stream` (~1679). `model_hub.Handler.do_GET` checks
  `_host_ok()` first, but `AHandler` answers these routes *before* calling `super()`, so the check never runs.
- **Scenario:** a page the person visits rebinds its hostname to 127.0.0.1 and reads `/api/arch/claudecode?run=cc...&since=0`. That
  returns every tool call and tool result of a Claude Code run, including any `.env` file the agent read, plus Studio chat history and
  the Managed Agent session list. The run id is guessable: `cc<milliseconds>`, also listed by `/api/arch/claudecode`.
- **Fix:** start `AHandler.do_GET` with `if not self._host_ok(): return self._send(403, {"error": "bad host"})` for every
  `/api/arch/` path, instead of repeating it per route. At the same time, wrap `int(since)` (claudecode, agents) in try/except: a
  non-number currently raises inside `do_GET` and the connection drops with no response.

### M4. The SDK may still hand Claude Code a subscription token (*plausible*)
- **Where:** arch_claudecode.py:48-53 `_env`, :360-361.
- **Scenario:** `_env()` drops `CLAUDE_CODE_OAUTH_TOKEN` from a *copy* and passes only two keys as `options.env`. The Python Agent
  SDK builds the CLI's environment as `{**os.environ, **options.env}`. If so, `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_AUTH_TOKEN`
  in the hub's own environment still reach the child, and a subscription login can be used. That breaks the module's central promise.
- **Fix:** override them explicitly: `env.update(CLAUDE_CODE_OAUTH_TOKEN="", ANTHROPIC_AUTH_TOKEN="")` in what is passed. Add a
  check that starts a fake transport and asserts the child environment has neither token.

### M5. Fleet state reads race with `os.replace` on Windows
- **Where:** arch_fleet.py:205 `_read`. It is called *without* `_LOCK` from `_agent_thread` (:439), `_stopping` (:415), `_watch` (:558)
  and `status()` (:627, polled by the hub). `_write` (:213) uses `os.replace`.
- **Scenario:** on Windows, `os.replace` fails with `PermissionError [WinError 5]` while another thread has the file open.
  - An agent thread's `_set_agent` raises, and its status write is lost or it lands in the generic error branch.
  - In `_watch`, the exception ends the watcher with verdict `not_sure` and no tests run, even though every agent finished.
- **Fix:** take `_LOCK` inside `_read` (it is an RLock, so nesting is fine) and retry `os.replace` on `PermissionError`. The same
  pattern exists in arch_claudecode.py `list_runs` (:275, reads meta without `_DISK`) and in arch_cloud `_add_spend` (H3).

### M6. A fleet agent can own the script the fleet uses as its proof
- **Where:** arch_fleet.py:62 `plan_check` / :133 `command_problem`. Test commands are `python arch_<x>.py`, run in the project root.
- **Scenario:** an agent's `files` includes `arch_hub_check.py` (or any `arch_selftest_*.py` named in `tests`). It edits it to end with
  `sys.exit(0)`, or it rewrites a helper the test imports. The fleet runs it and records `pass`. "The orchestrator verifies" becomes
  "the agent verifies itself".
- **Fix:** in `launch`, add a problem when any agent's owned path overlaps the script path of a planned test command, using `_overlaps`
  on the second token of the command. Optionally, compare the script's hash before and after and give `not_sure` if it changed.

### M7. Crew schedule: network calls while holding the schedule lock, and a follow-up can miss its own events
- **Where:**
  - arch_agents.py:253-281 `tick` calls `starter` (that is, `sessions.create` plus a thread) while holding `_SLOCK`.
  - :96-106 `send` posts the message *before* a new `_pump` opens the stream.
- **Scenario:**
  - A slow or hanging `sessions.create` (the SDK's default timeout is minutes) blocks every `/api/arch/crew_schedule` request and
    `_log_finished`.
  - In `send`, events emitted between the POST and the stream connecting are lost. A tool confirmation (`evaluated_permission == "ask"`)
    in that window is never answered, so the session sits in `requires_action` forever. A session in status `error` gets the message
    but no pump, so the page shows nothing.
- **Fix:**
  - In `tick`: under the lock, pick the due entries and write `last_slot`; release the lock; start the sessions; then re-take the lock
    to record `last_session`.
  - In `send`: pass the message to `_pump(c, sid, message)` (stream first, then send), and allow restarting from `error`.

## Checked and fine
- arch_claudecode run ids and file paths go through `RUN_ID_RE` before any path is built (`_run_path`), and fleet ids through
  `FLEET_ID_RE`: no path traversal.
- The hub validates the Claude Code `model`, `resume`, the chat `use`, and the agent/environment/repo ids.
- Every new POST route is behind the Host + Origin + token check in `model_hub.Handler.do_POST`.
- arch_fleet test commands: on Windows, `SHELL_BITS` covers `& | < > ^ %` and newlines, so CreateProcess cannot chain a second command.
- The arch_cloud reply cache never stores a cut-off reply (`max_tokens`) or a web-search answer, and it is off under eval and the
  self-tests.
- arch_fleet GPU queue: the lock order is always `_GPU_CV` then `_LOCK`, never the reverse, so it cannot deadlock. `finally` always
  releases the holder.
- The fast lane leaves the plan unchanged when it is off: every new key is added only under `if fast`.

## Suggested order
H2, H1 and H3 first: together they make the caps hold. Then H5 and M1 (the remaining cap leaks), H4 (training data), and M3 (hub
exposure). Each fix is small and local. The tests to add belong in the matching suites:
- `arch_selftest_cloud`: a concurrent `ultra` with a cap of $0.01, two processes writing spend, and a failure after a `pause_turn`.
- `arch_selftest_fleet`: an agent owning a test script, and a concurrent `_read` while `_write` runs on Windows.
- `arch_selftest_costs`: batch spend counted in the daily total.
- A dataset check: two tasks with the same 3000-character context head must stay as two samples.
