# This PC, 2026-11-04: where things live, what is eating the RAM, what to change

Source: `docs/pc_snapshot_20261104.txt` (server plan, `arch_hw.detect()`, drives, `live()`, top memory users), plus the numbers measured
on this laptop that are written down in CLAUDE.md. Every figure says what kind it is: **measured** here, **snapshot** (read once from
the snapshot), or **estimate** (arithmetic, not yet measured).

The machine: i5-13420H (4 performance cores with two threads each + 4 efficiency cores = 12 threads), RTX 4050 Laptop with 6 GB, 32 GB
RAM, one 1 TB NVMe SSD (C:), and two USB drives (D:, E:).

## In short

1. **The RAM is full because the heavy model lives in it.** The biggest program on the machine is one llama-server at 12.5 GB: the
   heavy MoE model kept "beside the worker", with 11.6 GB of its experts in RAM. Turning that off (or turning the new fast lane on)
   gives back about 12 GB. The price is a 15-20 s wait the first time a step needs the heavy model.
2. **Keep everything Architect uses on C:.** It is the only fast, internal, trustworthy drive. D: is a small slow FAT32 stick (good for a
   spare copy of small files only). E: may not be the size it says it is, so nothing goes on it until it has been checked.
3. **Keep the speed settings that were measured to work** (n-gram speculative decoding, q8_0 cache, the 800-token thinking budget).
   Try the fast lane when you want the worker to answer as quickly as possible and do not mind the heavy model loading on demand.

## 2. Where each kind of data should live

| Data | Where | Why (numbers) |
|---|---|---|
| Model files (GGUF, Ollama blobs) | **C:** `C:\Users\alexi\.ollama\models` (where they are now; llama-server reads Ollama's own blobs, no second copy) | Loading a model reads several GB; NVMe is the only fast drive here. The heavy file alone is ~12-14 GB, over FAT32's 4 GB per-file limit, so it could not even go on D:. 223 GB free on C: (snapshot). |
| KV / slot caches (`hub_data/server/slots/<tier>`) | **C:** (default) | Saved prefill for the long, unchanging start of each prompt; read back on every repeat, so it must be fast. Tens to hundreds of MB. |
| N-gram lookup cache (`hub_data/server/lookup/worker.bin`) | **C:** (default) | Read by the worker on every token it guesses; this is what took edits from 56 to 306-343 tokens/s (measured). |
| Reply cache (`arch_cache`) | **C:** (default) | Small, read on every call at temperature 0 or with a seed. |
| Logbook / ledger / jobs.db / index.db | **C:** (default) | SQLite and JSON written during runs; a USB stick that is unplugged mid-write can corrupt them. |
| Training exports (`dataset`: SFT, preference pairs, trajectories) | **C:**, with a spare copy on **D:** | Plain text, small. D: is fine as a backup copy (files stay far below 4 GB), never as the only copy. |
| Archives (`storage.archive` write-behind) | **C:**, optional copy to **D:** | Same reasoning; old runs are rarely read, so a slow stick is acceptable for the copy. |
| Anything | **not E:** | E: reports exactly 1,000,000 MiB, the pattern of fake-capacity drives (snapshot flag). Run the drive check (`arch_hw.measure_drive`) on it before trusting it with anything. |

## 3. Settings to change, each with the number it rests on

| Setting | Today | Suggested | Rests on | Expected gain |
|---|---|---|---|---|
| `server.heavy_beside` | auto (heavy beside the worker) | **off** while the RAM is tight; auto when you plan a lot and the RAM is free | measured: beside = 14-16 tok/s for the heavy model and ~1 s to switch; separate = a 15-20 s load per escalation. Snapshot: it holds 12.5 GB RAM + 2.25 GB VRAM | ~12 GB RAM and 2.25 GB of graphics memory back; 15-20 s extra each time the heavy model is needed |
| `server.fast_lane` (new) | off | **on** when you want the quickest worker replies (it also implies heavy beside off) | the parts already measured: n-gram speculation 56 -> 306-343 tok/s on edits; the worker already fits whole at 8192 (2.92 GB, plan) | the ~12 GB above, plus priority and performance-core pinning for the worker. Their own effect on speed is **not measured yet** (estimate: small while the PC is idle, larger while tests, a browser or a build compete for the CPU). Compare tok/s in the console strip with it off and on. |
| `server.fast_think_budget` (new) | 256 | keep | measured: an unlimited planner thought ~3000 tokens before a ~200-token plan. Applies only when the worker thinks at all (its profile normally answers directly) | fewer wasted reasoning tokens on the worker when thinking is on |
| `server.ngram` | auto | **keep** | measured 56 -> 306-343 tok/s on edits | already in place |
| `server.draft` | auto | **keep** (not try) | measured: qwen3:0.6b as a draft gave 66-78 tok/s on new code and 125 on edits, below the n-gram cache | avoids a slower setup and its extra graphics memory |
| `server.kv` | q8_0 | **keep** | half the size of f16 with almost no loss (setting description); q4_0 shows a loss on code | the 8192 window costs ~0.6 GB instead of ~1.2 GB for the 4B worker (estimate from its shape) |
| `server.cache_ram` | 0 (auto = 2048 MiB per server on 32 GB) | 1024 if the RAM stays above 85 % after the heavy change | snapshot: the worker's llama-server holds 2.3 GB | ~1 GB per non-router server (estimate); slightly fewer saved prompts in RAM, the slot files on C: still cover repeats |
| `server.ctx` | 0 (profile: 8192) | 12288 only when the heavy model is NOT beside the worker | estimate: worker ~2.3 GB weights + ~0.6 GB KV per 8192 tokens at q8_0; with the card to itself there is ~4.9 GB usable | room for bigger prompts without cutting project context; measure with `server plan` first |
| `server.think_budget` | 800 | keep | measured: ~3000 tokens (2-5 minutes) without a limit | already in place |
| `behavior.tests_on_ecores` | auto | keep | tests on cores 8-11 leave cores 0-7 for the model servers (`arch_hw.ecore_mask`) | the fast lane pins the worker to cores 0-7; the two fit together |
| `behavior.heavy_jobs` | one at a time | keep | measured: four live runs at once on one 8192 window broke each other, and a full suite + a second suite + the oracle + a GPU benchmark at once crashed this laptop | stability |

What is deliberately **not** suggested: changing the Windows power plan, Defender, the HP control app, Docker/WSL limits, or anything
else outside Architect. The fast lane raises only its own worker process's priority, and `fast_lane = off` puts it back at the next
server start.

## How to check the gains

1. `python architect.py server plan` before and after each change: it says "Fast lane is on" and lists what changed.
2. The console strip's tokens/s on the same edit task, off vs on.
3. Task Manager > Memory, before and after `heavy_beside = off`: expect about 12 GB freed (snapshot figure).
