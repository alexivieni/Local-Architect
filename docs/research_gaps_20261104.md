# Research: templates, pipeline visibility, eval rigor, sandboxing, self-improvement (2026-11-04)

## Area

### Proposals
- Ship 6 to 8 first-party templates in a 'New project' gallery in Projects: SaaS API (FastAPI+SQLite+SQLModel/Alembic), Flask+HTMX CRUD/admin, stdlib CLI, data pipeline (SQLite/CSV+pytest), math/notebook-style lib, and background-job worker. Each card should show a file tree, a short spec and a one-click start.
- Each template carries an AGENTS.md conventions file, a passing test suite, a `make check` / `just check` (ruff, mypy-lite, pytest) and seed fixtures. Architect's flow gates then run the template's own check command instead of generic heuristics.
- Make billing and auth swappable modules that start in offline mock mode: local session auth plus a fake payment provider whose interface matches Stripe test mode (sk_test_, card 4242). Users get a working SaaS flow without network access or keys.
- Default to Python/SQLite/HTMX stacks for the gpu6 small-model class, and label heavy JS-framework templates 'needs larger model'. Since no benchmark compares frameworks directly, use the 109-task eval harness to measure per-stack pass rates on the local Ollama models.
- Add template-derived tasks to the eval harness (add a CRUD endpoint + migration + test, add an admin page, add a job) so you can see whether templates actually raise agent success.
- Keep the file layout small and predictable (app/, tests/, migrations/, scripts/) with a 'where things go' map in each template, so small-context models can find files without searching.

### Findings
- Lovable presents templates as a gallery of 80+ starting points covering SaaS apps, internal tools, dashboards and portfolios. Its stack is fixed: React frontend, Supabase Postgres/auth/storage, and Stripe. (https://lovable.dev/guides/bolt-vs-replit-vs-lovable)
- App builders treat billing as an integration you switch on in test mode, not as code the model writes from scratch. Bolt.new takes an sk_test_ key in a Stripe settings panel and generates checkout and webhook code. You test with card 4242 4242 4242 4242, and webhooks need a public URL. (https://www.rapidevelopers.com/bolt-ai-integrations/stripe, https://girff.medium.com/-038704f54099)
- The FastAPI/SQLModel/Alembic/pytest/GitHub Actions set is the de facto Python SaaS-API starter. The official full-stack-fastapi-template adds React, Postgres, Docker and automatic HTTPS. (https://repos.ecosyste.ms/topics/sqlmodel, https://github.com/fliden/starter-fastapi)
- Small open code models do better in Python than in less common languages, and larger small models are more correct and more stable. (https://arxiv.org/html/2507.03160v3)
- How well a model codes in a language tracks how popular the language is, because popular languages have more training examples. (https://hackernoon.com/lang/si/comparing-llms-coding-abilities-across-programming-languages, https://arxiv.org/pdf/2505.24324)
- I found no benchmark that compares heavy JS frameworks with Python frameworks for small models. The case for stdlib/Flask/FastAPI/SQLite/HTMX on small local models is an inference from the language and popularity results above, not a measured result. (https://arxiv.org/html/2507.03160v3)
- Bolt's backend is Node/Express only, and Replit pairs its agent with a full IDE. Each tool picks one opinionated stack per template rather than asking the user to choose. (https://lovable.dev/guides/bolt-vs-replit-vs-lovable)
- Starters that ship lint, type-check, test and CI commands (just/uv, Ruff, mypy, pytest with coverage) hand an agent ready-made checks to verify its work against. That fits Architect's code-gate flows. (https://github.com/fliden/starter-fastapi)

## Area

### Proposals
- Run view, built from the existing flow trace. Show the YAML flow as a vertical step list by default and offer a graph toggle. Each step shows a live status chip (waiting, running, passed gate, failed gate, skipped), the model name, its token budget against tokens used, elapsed time, and retry count. Clicking a step opens its input, output, gate result and log, using the GitHub, Dify and Temporal patterns.
- Timeline tab for each run: a Temporal-style row per step on a time axis, coloured by gate outcome, so slow steps and retries on the 6GB GPU are easy to see. Add a 'Failed here, because...' callout that names the gate that failed and its message.
- Plain-language flow editor. Edit steps in a form generated from a schema, never as raw YAML by default. Validate on every change (unknown model, budget larger than the context window, missing gate) with an inline sentence explaining the fix. Saving creates a new flow version with a diff and a one-click revert, following LangGraph Studio's versioned save.
- Settings explained inline. Every setting gets a one-line plain description, its effect ('higher = slower but more thorough'), its default, and a 'reset to default' button. Group the advanced settings behind an expander. Show the model each role resolves to on the Models page.
- Pause and edit for human checkpoints. Let a run stop at a gate, show the proposed plan or diff, let the user edit or approve it, and record the edit in the run log, like a Claude Code plan or todo list.
- Rerun from a step: retry a failed run from the failed step with the same inputs (n8n style). Keep the run history so two runs can be compared side by side (models, tokens, gate results), which also ties into the 109-task eval reports.

### Findings
- GitHub Actions shows each run as a live graph. Each job is a node with a status icon, lines show dependencies, and you click a node to see its logs. (https://docs.github.com/en/actions/how-tos/monitor-workflows/use-the-visualization-graph, https://github.blog/changelog/2020-12-08-github-actions-workflow-visualization/)
- Temporal's UI gives the same run history in three views: Compact, Timeline and Full History. On the timeline, related events are grouped into one span coloured by outcome (green completed, red failed). Every view updates live as new events arrive. (https://temporal.io/blog/lets-visualize-a-workflow, https://temporal.io/blog/the-dark-magic-of-workflow-exploration)
- Dify's run trace shows, for each node, its input and output, token use, run time, the order nodes ran in, and the exact node that failed and why. Each node's settings panel also has a 'Last run' tab. (https://docs.dify.ai/en/use-dify/debug/history-and-logs, https://docs.dify.ai/guides/workflow/debug-and-preview/log)
- LangGraph Studio shows the agent graph and marks which node is running, done or skipped. You can inspect state before and after each step. A gear icon on a node opens its config fields (for example the prompt), and saving creates a new assistant version or overwrites the current one. (https://docs.langchain.com/langgraph-platform/iterate-graph-studio, https://changelog.langchain.com/announcements/ann_GGhdB0eCxsmuh)
- Saving an edit as a new version, instead of overwriting in place, is a common safety net that makes undo and comparison easy. (https://docs.langchain.com/langgraph-platform/iterate-graph-studio)
- Pausing a run so a person can edit its state, then validating and recording that edit before resuming, is the recommended human-in-the-loop pattern. (https://notes.kodekloud.com/docs/LangGraph/Advanced-Control-and-Debugging-UX/Enabling-State-Editing-Mid-Execution/page.md)
- n8n keeps a list of past runs. Opening one shows each node's input and output, and a failed run can be retried with the same trigger data. (https://www.rapidevelopers.com/md/n8n-tutorial/how-to-view-execution-history-in-n8n)
- Graph versus list: the graph views (GitHub, LangGraph) work best for showing dependencies and branches. The timeline and list views (Temporal, Dify trace) work best for order and duration. Mature tools offer both views of the same data rather than picking one. (https://temporal.io/blog/lets-visualize-a-workflow, https://docs.dify.ai/en/use-dify/debug/history-and-logs)
- Showing per-step model, tokens, cost and latency in the trace is standard practice in LLM workflow tools. (https://docs.dify.ai/en/use-dify/debug/history-and-logs)

## Area

### Proposals
- Eval statistics module (stdlib only): every A/B run reports paired per-task deltas, the exact McNemar p-value on discordant pairs, a cluster bootstrap 95% CI (clustered by fixture repo or task family), and a minimum-detectable-effect line. In the hub, any 'improvement' whose CI crosses 0 is shown as 'not distinguishable from noise'.
- Eval protocol: fix seeds and temperature per run and record them, run k>=3 epochs per task and average within each task, and freeze about 30% of the 109 tasks as a held-out split that no tuning loop ever sees. Add a contamination check: hash the task prompts and refuse tuning traces that contain held-out task text. Rotate in fresh, private tasks each quarter.
- Windows sandbox in three layers via ctypes: (1) a job object with KILL_ON_JOB_CLOSE, memory, CPU-time and active-process limits, assigned at CREATE_SUSPENDED with no breakaway; (2) a restricted or low-integrity token, or AppContainer, so writes are limited to the project workspace; (3) network denied by default through an AppContainer without internetClient, with a per-run 'allow network' toggle shown in Settings. On Linux use bubblewrap (--unshare-net, read-only root, rw workspace bind); on macOS use a sandbox-exec profile. Show a one-line sandbox status badge in Workspace.
- Offline GEPA-style flow tuner: collect failing traces from code gates, have the local model write a reflection and propose edits to role prompts or flow YAML, then score each candidate on the tuning split. Keep a Pareto front per task family and promote a candidate only if the paired McNemar/bootstrap test on the held-out split shows a non-negative CI. Store every candidate with a diff and a rollback in the hub.
- Self-play test generation with guards: generated tests count only if they fail on a mutated or stub implementation and pass on a reference solution (mutation-kill check). Never let the same run author both the solution and its acceptance gate.
- Budget and safety rails for self-improvement: cap the number of rollouts per tuning session (sized to the RTX 4050 6GB), keep one edit per candidate for attributability, and never auto-modify gates, sandbox config or the eval harness. Those are human-approved changes only.

### Findings
- For comparing two configurations on the same tasks, analyze per-task paired differences, not two separate aggregate scores. Pairing removes variance from task difficulty and shrinks the standard error. (https://arxiv.org/abs/2411.00640, https://anthropic.com/research/statistical-approach-to-model-evals)
- Related tasks, such as several tasks built on one fixture repo, must use clustered standard errors. Naive SEs can be 3x or more too small. (https://anthropic.com/research/statistical-approach-to-model-evals)
- Run repeated samples (epochs) per task and average them inside each task before comparing. This cuts the within-task sampling noise that dominates small local evals at temperature > 0. (https://arxiv.org/abs/2411.00640)
- With binary pass/fail on the same 109 tasks, the exact McNemar test on the discordant pairs is the correct significance test. A paired bootstrap over tasks, resampled by cluster, gives a CI on the pass-rate delta. (https://arxiv.org/abs/2411.00640)
- Do power analysis before an experiment. It tells you the smallest effect 109 tasks can detect, so you don't chase noise. (https://arxiv.org/abs/2411.00640, https://pypi.org/project/errorbars/)
- On Windows, a job object gives process-tree containment, memory/CPU/process-count limits and kill-on-close. It does NOT isolate the filesystem or network. (https://docs.rs/crate/roboticus-agent/latest/source/src/sandbox_windows.rs, https://raw.githubusercontent.com/Hmbown/CodeWhale/main/docs/SANDBOX.md)
- Assign the job at spawn time (CREATE_SUSPENDED, then assign, then resume) and leave BREAKAWAY_OK clear. Otherwise a child can create grandchildren outside the job. (https://docs.rs/crate/envseal/latest/source/src/sandbox/windows.rs)
- Network blocking on Windows without admin is best done with an AppContainer (no internetClient capability) or a less-privileged/restricted token. Per-program WFP/firewall rules need elevation. (https://raw.githubusercontent.com/Hmbown/CodeWhale/main/docs/SANDBOX.md)
- On Linux, bubblewrap (unprivileged user namespaces, --unshare-net, read-only binds) is the usual no-Docker sandbox. On macOS, sandbox-exec with an SBPL profile, though deprecated, is still what agent CLIs use for file and network denial. (https://github.com/containers/bubblewrap, https://github.com/anthropic-experimental/sandbox-runtime)
- Trace-reflective prompt optimization beats Bayesian instruction search and RL with far fewer rollouts. GEPA reads failure traces, has an LLM propose edits, and keeps a Pareto set of candidates. (https://arxiv.org/abs/2507.19457)
- MIPROv2 jointly optimizes instructions and few-shot demos with Bayesian optimization over a validation set. It is a cheaper, mature baseline when the metric is a code gate. (https://arxiv.org/abs/2507.19457, https://dspy.ai)
- The main risk of self-improving loops is overfitting to the optimization set. Gains measured on the same tasks used to tune are inflated, so a frozen held-out split is mandatory. (https://arxiv.org/abs/2507.19457, https://arxiv.org/abs/2411.00640)
- Self-generated tests (self-play, agent-written tests) can be gamed. A model that writes both the code and the tests can make them agree trivially. Generated tests need independent validation, such as mutation testing or a reference solution. (https://arxiv.org/abs/2411.00640)
