Small local models are not deterministic: the same code can pass a task on one run and miss it on the next (test-calc-05 passed in the baseline and failed in the second run with no related change). Read single tasks as signals, the totals as the trend.

Reading the saved runs showed that several failures were not wrong code. A machine problem ended the run instead: the larger 14B model gave no answer while it loaded beside the worker (two build tasks), and the model server restarted mid-run (one project). When runs shared the server, its 8,192-token memory also filled up in the middle of a reply. This release makes each of these something the run recovers from: the step goes back to the worker model, and a reply cut off at the memory limit keeps its finished files.

03

What changed since v12

Runs on any laptop, offline

A resident local model server (llama.cpp) with Ollama as fallback, four model tiers chosen from the models already installed, a measured "passport" for each model, and installers per hardware class. Nothing reaches the internet unless the person turns it on.

Workflows as data

All 25 workflows (build, bug fix, refactor, test, security, CI and more) are YAML files with named code checks and hard budgets for calls, tokens and time. Adding a workflow means adding a file and its test tasks.

Tools, memory and retrieval

The model can search, list, read and run tests on its own, and keeps short dated notes that earn trust only when later runs pass. Code search uses SQLite full-text search, with no vector database.

Works through a queue on its own

A supervisor runs queued tasks inside daily limits, retries a failure with a different approach, pauses when the model server is down, and stops on a kill switch.

One-screen interface

What was asked on the left, what the machine is doing on the right (plan, tool calls, checks, verdict), a command palette, light and dark themes, and an HTML receipt per run.

Measured, not claimed

A benchmark harness of 109 tasks across 15 families, with a regression gate: a self-improvement that lowers the pass rate is refused automatically.

04

This release: small models finish more

Every item below came from watching the 4B model fail a benchmark task and fixing the harness rather than the model.

  • Change one function, keep the rest. A new edit block replaces exactly one function; whole-file rewrites used to drop code an earlier step had built.
  • Interface first. The plan lists every public function and its arguments before any code is written, and every step sees that list.
  • One module, one step. Small requests run as a single step, so finished work is not lost in a hand-off.
  • A bad try cannot undo a good one. A try that breaks the code or passes fewer tests is reverted byte for byte, and the model is told what still fails.
  • Failures explain themselves. After a failed run the model writes a short post-mortem, and the next retry starts from it.
  • Tests and refactors that count. A half-right test file keeps its good tests; a refactor that only re-spaced the code is rejected.
  • Every prompt fits the model it goes to. Before sending, the whole prompt is measured against the model's real memory and room is kept for the answer; the least relevant files are trimmed first.
  • A reply with just the changed functions is applied. It used to be refused as "would cut the file from 30 to 8 lines", losing the try.
  • Tests from the first step. When a request asks for tests, the first step writes them and no step passes while there are none.
  • A larger model only when it can help in time. On this laptop the 14B writes about 2.5 tokens a second, about ten minutes an answer, so a stuck step stays on the worker unless the larger model can answer within a set limit.
  • The GPU, visible and better used. The console shows live how busy the graphics card is and warns when a model spills into RAM; mixture-of-experts models keep every layer on the card with only some experts in RAM; a speed-up "draft" model is found among installed models only when its tokenizer matches exactly; model servers start only when a run uses them.
  • An overnight benchmark. architect.py eval --set representative runs the same 17 live tasks every time and compares task by task with the previous run; the hub's new Benchmarks page charts every run.
  • One heavy job at a time. Test suites, benchmarks and tuning run below normal priority and wait for each other, so the laptop is never asked to do four at once again (it crashed once today when it was).
  • The tests that judge a bug fix are read-only. The model can no longer put its reproduction inside the existing tests or edit them to make a fix pass.
  • Machine problems no longer end a run. If the larger model does not answer, the step goes back to the worker; if a reply fills the model's memory, its finished files are kept and the model is asked for a smaller change; the model server now says how many conversations it holds, so they can no longer overflow a shared memory.
  • Reliability fixes. A test that leaves a server running is stopped at its time limit (it used to hang for hours on Windows), a crashed model server is restarted mid-run, and two runs from one install no longer collide on a shared file.
05

Known limits

  • Not every live task was re-run on the final code. All 17 take about two hours on this laptop, and model work cannot run in parallel there (see below). Five were re-run on this release's fixes; the last fixes (how the model server sizes its memory, and how a reply that fills it is kept) are verified by the automated checks only.
  • Whole projects are still the hardest. A 4B model rarely finishes a multi-file project with a working test suite on its own; this is where the next work goes.
  • One task at a time per model server. Running four benchmark batches at once overflowed the server's shared memory and broke them; that case is now fixed in the app's own server start-up, but parallel model work on a 6 GB card stays limited.
  • Three security self-checks fail on this machine only. They need a local web server on port 8000, which times out here, and they fail the same way on the untouched v12.
  • The YAML version of the bug-fix workflow (an opt-in engine) does not yet keep the existing tests read-only; the default engine does.

Try it

Unzip architect_v13_7_20261103.zip; Python 3.10 or newer, standard library only. Start the hub with START_HUB.bat, or use the command line:

python architect.py ready                  # first run: detect the machine, pick models, prove it works
python architect.py run "add a --json flag"  # one task
python architect.py eval --fake --quick      # the benchmark harness, no GPU needed
python architect.py selftest --suite full    # every automated check
