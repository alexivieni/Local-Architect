# Architect as a small distributed system: proposal for the owner

Date: 2026-11-04. Scope: `C:\Users\alexi\Downloads\architect_v12\architect`. Status tags: numbers marked **[confirmed]** were checked against the source by a verifier. **[unverified]** means the researcher reported it but no verifier checked it. **[estimate]** is arithmetic on this machine's numbers, still to be measured. **[code]** is a fact read from Architect's own source.

---

## 1. The principle in one paragraph

Architect should behave like a small cluster scheduler that runs on your own machine. A cloud harness can assume one large GPU. Architect cannot, so it treats every part of the computer as its own node with its own speed: the graphics card, the performance and efficiency cores, the RAM and its bandwidth, each drive, the battery, and any other machines on the network. It runs one loop, the same on every machine:

- **detect** what is there;
- **measure** how fast each part really is, without trusting a model card;
- **place** each model tier on the parts where it runs fastest, choosing quant, context and split;
- **schedule** the work so the parts overlap: the GPU writes while the CPU runs tests, and the next model loads while the current step finishes;
- **explain** each decision in one plain sentence;
- **re-plan** when something changes: charger pulled, monitor moved, drive removed, a better model installed.

Code, data and math can all be checked by running them. So small models plus strong checks are enough, provided the machine is kept busy and swaps are cheap. Your HP Victus is the worked example. On it the plan is: router on the CPU, a 4B worker that lives on the 6 GB card, and a 35B mixture-of-experts (MoE) heavy model that streams its experts from 32 GB of dual-channel RAM. The same loop must also give a sensible plan for a CPU-only 8 GB laptop, a 128 GB Mac, or two desktops on a LAN.

## 2. The machine map

### 2.1 What each part is for

| Part | What Architect uses it for | Measured or detected today | Gap |
|---|---|---|---|
| **Discrete GPU** (NVIDIA, AMD, Intel Arc, Apple) | The worker sits fully on the card. Attention and shared weights of the heavy MoE also go here, and the card processes prompt batches even for layers held in RAM (llama.cpp op offload, on by default **[confirmed]**, README) | NVIDIA only, via nvidia-smi **[code]** | AMD and Intel on Windows are not detected. Live numbers exist only for NVIDIA, so "make room" never fires on other vendors **[code]** |
| **iGPU** (your Intel UHD) | Drives the display, so the 4050 stays at 0.2 GB used. It could later run a router or embedding model on Vulkan, but only after a bench: it shares RAM bandwidth with experts kept in RAM | Invisible to Architect **[code]** | List all adapters, mark the one driving displays, re-plan when a monitor moves |
| **P-cores** (4 on the i5-13420H) | Generation threads for RAM-held layers and the CPU router | Detected (EfficiencyClass) **[code]** | No affinity pinning, and `--threads-batch` is never set |
| **E-cores** (4) | Tests, linters, scanners and sandbox runs at low priority, so they never steal P-cores from generation | Idle during generation **[code]** | Pin gate subprocesses to E-cores |
| **RAM** (32 GB DDR4-3200, dual channel) | MoE experts, the OS page cache acting as the warm model cache, the prompt-state cache (`--cache-ram`), the Docker/WSL VM | Size and free memory detected. Bandwidth is a constant of 50 GB/s **[code]** | Derive measured bandwidth from real runs. Your 14B at 5.1 tok/s implies about 22-24 GB/s effective, against 51.2 GB/s theoretical **[estimate]** |
| **Drives** | Storage roles (2.2) | Only free space on the models drive **[code]** | No drive list, no per-drive read speed, no bus or media type |
| **Power and heat** | Plan lighter on battery or when hot | Battery and GPU temperature recorded, never acted on **[code]** | Throttle reasons, CPU temperature, speeds keyed by power state |
| **LAN machines** | Whole roles or jobs: the heavy tier on a desktop with a bigger card, eval batches | Ollama hosts added by hand, sized by a regex on the model name **[code]** | Add llama-server hosts, measured speeds, cost-based routing. Known bug: escalation sends a remote role back to the local server |
| **NPU** | Report only. llama.cpp does not use it | Not detected | Detect, and say so plainly |

**Why bandwidth decides speed.** Generating a token reads every active weight once. For any tier, speed ≈ min(GPU bandwidth ÷ bytes on the GPU, RAM bandwidth ÷ bytes in RAM). From your own runs: the 4B at 68 tok/s implies about 170 GB/s of effective GPU bandwidth. The constants Architect uses today predict about 9.4 tok/s for the 14B split, nearly twice the 5.1 measured **[estimate]**. Measured numbers have to replace the constants before any of the planning below can be trusted.

### 2.2 Storage roles

Architect should give each drive an explicit role, as a setting with undo. Today slots, logs, the lookup cache and test sandboxes all land wherever the data folder happens to be **[code]**.

| Role | Needs | On your machine |
|---|---|---|
| **Model store** | Fast sequential reads, and not near-full QLC | New NVMe, once fitted and measured |
| **Warm cache** | RAM. The OS page cache keeps recently read model files, so a restart reads from RAM | 32 GB RAM, plus a low-priority prefetch of the heavy model's file when escalation becomes likely |
| **KV / slot store** (`--slot-save-path`, saved prompt states) | Fast random writes | New NVMe |
| **Scratch / worktrees** (parallel attempts, sandbox copies, package caches) | Random writes, and space for N copies of a repo | New NVMe |
| **Archive / backup** (old models, run receipts, exports) | Capacity, speed does not matter | Crucial P3 |
| **Not for models** | Anything on a USB 2.0 bus or under about 100 MB/s | The USB stick |

**What a second NVMe adds, honestly.** It will not make generation faster: once a model is loaded, the drive is no longer involved. It helps in three ways.

1. Model loads get shorter, but only if the new drive reads faster than the P3's 1.6-2.0 GB/s. Raw read is about half of today's start times: a 9 GB file is about 4.5-5.6 s of reading against 9.6 s measured **[estimate]**. Expect a second or two off the heavy-tier start, not a revolution.
2. It separates traffic. Test sandboxes and slot saves stop competing with model reads on a QLC drive that slows down as it fills.
3. It adds capacity, so you can keep several quants of each model side by side for the quant ladder (section 4) without filling the P3.

Recommendation: new NVMe for models, slots and scratch; the P3 for archive. Moving models means copy, verify sha256, then ask before deleting anything or changing `OLLAMA_MODELS`.

**What the USB stick adds: almost nothing for this work.** At 20-23 MB/s, a 9 GB model takes about 7 minutes to read **[estimate]**. A stick sold as "1 TB" that runs at USB 2.0 speeds is often fake capacity. Architect should flag it "not for models" and offer a capacity check, run only after your explicit yes. The check writes numbered blocks and reads them back, and deletes only its own files. Until the check passes, use the stick only for copies of data you also have elsewhere.

## 3. The resource manager and scheduler

### 3.1 First, a correctness gap that changes your numbers

In llama-server mode the heavy tier is never started during a real run. `ensure()` starts only resident tiers, so heavy calls fall through to Ollama **[code]**. Ollama splits by whole layers and has no `--n-cpu-moe`. So your 15.4 tok/s MoE figure, and what real runs actually get, comes from the slower placement. This is fix number one tonight.

### 3.2 Three levels of "how warm is a model"

Serving research measured the same three cost levels:

- already on the card: about 0.04-0.25 s to the first token;
- swapped in from RAM: 2.4-3.1 s;
- cold start: 146-208 s, on 27-42 GB FP32 models.

**[confirmed]**, NVIDIA, https://developer.nvidia.com/blog/cut-model-deployment-costs-while-keeping-performance-with-gpu-memory-swap/

Keeping the process alive is a separate saving from keeping the weights loaded. In vLLM, a sleeping process wakes in 0.26-0.85 s against 37.6-58.1 s from cold, and five model switches took 357 s without sleep against 113 s with it **[confirmed]**, https://vllm.ai/blog/2025-10-26-sleep-mode. Your starts (5.7 s for the 4B, 9.6 s for the 14B, 13.7 s for the MoE) sit between the RAM level and the cold level.

So the scheduler tracks four states per tier: resident, sleeping (process kept), in page cache, and on disk. It also knows the measured cost of moving from each state to each other state.

### 3.3 The mechanisms already exist, the policy does not

Current llama-server already has:

- a router mode with load/unload endpoints, LRU eviction and `--models-max` (default 4);
- `--sleep-idle-seconds`;
- `--cache-ram` (default 8192 MiB) for prompt states kept in RAM;
- `--slot-save-path`;
- `/health` returning 503 while loading.

**[confirmed]**, https://huggingface.co/blog/ggml-org/model-management-in-llamacpp, https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md

What is missing is a policy that knows the work ahead. LRU forgets that the planner will be needed again in two steps. KVFlow evicts by "steps until needed" over the agent's step graph and beats a radix-cache baseline by up to 1.83x on one workflow and 2.19x with many **[confirmed]**, https://arxiv.org/abs/2507.07400v1. Architect's YAML flows give it that step graph for free.

### 3.4 The new module: `arch_resources.py`

It sits behind `arch_server.plan()` and does six jobs.

1. **Joint placement.** Today each tier is fitted alone against the whole card, so starting the heavy tier beside the worker overcommits VRAM **[code]**. The new solver works over tiers × devices × residency. Constraints: the sum of VRAM on each device stays at or under measured free memory, the RAM budget is kept, and the Docker/WSL VM keeps room to grow. Output: which tiers can sit together, which must swap, and the measured cost of each swap.
2. **Swap by measured cost.** Swap only when (time saved by the better model × chance it is needed) > (load cost from where its bytes are now) + (cost of re-reading the lost prompt). Heavy steps are grouped while the heavy model is loaded, which generalises today's `defer_judge`. The fixed rules ("fits whole", "VRAM < 10 GB") go.
3. **Save and restore slots.** `--slot-save-path` is configured but nothing calls save or restore **[code]**. The worker's slot is saved before a step-aside and restored after, and only kept when restoring is measured faster than re-reading the prompt.
4. **Admission control.** One dispatcher with per-tier queues and priorities: an interactive run first, then Studio, then autopilot and eval. When the queue is full you see "busy: your run is 2nd in line, about 40 s" instead of a timeout. A second run is refused if it would shrink a running run's window. Four runs on one 8192-token window already broke each other once. Ollama (queue limit 512, then 503) and llama-server (503 while loading) give the building blocks **[confirmed]**, https://docs.ollama.com/faq.
5. **Failure handling.** The watchdog checks speed against the passport, not only whether the server is alive. On Windows the NVIDIA driver can quietly spill VRAM into system RAM, so an overcommitted card shows up as a 3x slowdown, not a crash **[unverified]**: the NVIDIA page returned 403. Jobs checkpoint at step boundaries. A chaos selftest kills the worker mid-reply, fills the queue and fakes an overcommit.
6. **Re-planning.** A watcher on the existing 5-second recorder compares each sample with what the plan assumed. Triggers: charger state, desktop VRAM changed by more than 0.5 GB, the VM growing, a model's drive gone, free RAM low. It proposes a new plan with undo, or applies it between steps when no slot is busy.

### 3.5 Overlap: keep every part busy

Today a run goes strictly call → apply → run tests → next call. The GPU idles while tests run, and the CPU idles while tokens are generated **[code]**. Three fixes:

- **Pipelined best-of-N.** Check candidate *i* on the E-cores while candidate *i+1* is being written.
- **Prefix pre-warm.** While tests run, send the next prompt's fixed first part with `n_predict 0`, so the next call starts with its prompt already read. On local hardware, re-reading the prompt is the hidden cost: a 35B MoE took 155 s to re-read 40K tokens and 6 s with a restored cache **[unverified]**, community measurement.
- **Placement of the work itself.** llama-server stays on the P-cores, tests run on the E-cores at below-normal priority, and RAM-heavy tests never run while the RAM-bound MoE is generating.

### 3.6 Utilization reporting

Each run gets a timeline with one lane each for GPU compute, VRAM, P-cores, E-cores, estimated RAM bandwidth, disk, and battery/temperature. Every idle gap is labelled: waiting on a test, loading, swapping, queued, throttled, or unexplained. A headline sentence goes on top, for example: "The graphics card sat idle 41% of this run, mostly while tests ran." The goal is "unexplained" under 10% of wall time.

### 3.7 Several machines

Give whole roles and jobs to other machines; don't split one model's layers across them. Splitting layers over 10 GbE made prompt reading faster but generation slower: 11.1 → 5.9 tok/s on a 72B **[unverified]**, https://github.com/kjaiswal/llama-cpp-distributed-benchmarks. The llama.cpp RPC README warns it must never run on an open network. The rules:

- hosts gain a kind: Ollama, llama-server, or rpc;
- each host is measured: tok/s, round-trip time, link speed;
- the same cost model picks the host for each role;
- RPC is offered only for a model that fits on no single machine, with its warning and an explicit yes;
- generated code always runs in the local sandbox.

## 4. Quantization and placement

**In plain words:** quantization means storing each weight in fewer bits. Fewer bits mean a smaller file, so more of the model fits on the card and the RAM part is read faster. Between 4 and 8 bits the quality loss is small. The choice is mostly about where things fit, so Architect makes it per tier and per device, by measurement.

### What the evidence says

- **4-bit is close to lossless for coding work.** On Qwen3.8-27B, Terminal-Bench 2.1, Q4_K_M (17 GB) matched BF16 (55 GB), and 2-bit showed "a noticeable fall" **[confirmed, with a correction]**: Q8_0 was run on GPQA and IFBench but only interpolated on Terminal-Bench. https://quesma.com/blog/qwen38-27b-quantizations-benchmarked/
- **For a 35B-A3B MoE**, measured mean KLD (KL divergence, how far a quant's predictions drift from full precision) against size: Q4_K_M 0.019 at 18.5 GB; Q3_K_M 0.032 at 15.5 GB; IQ3_XXS 0.050 at 13.1 GB **[confirmed]**, https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks. The same quant name from another uploader scored 0.085, so measurements are keyed by file hash, not by name.
- **On a GPU, smaller stops meaning faster below about 4.5 bits per weight.** It buys room, not speed **[confirmed]**, https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md.
- **On a CPU, IQ formats can be 2-4x slower than K-quants.** M2 Max: IQ3_XXS 6.26 tok/s against Q4_K_S 17.55 **[confirmed]**, https://github.com/ikawrakow/ik_llama.cpp/discussions/164. Your MoE heavy tier is an IQ3 build with its experts on the CPU, so a bigger K-quant may well be faster. That is a hypothesis to measure.
- **KV cache** (the model's working memory for the conversation). Since llama.cpp PR #21038 (April 2026), a quantized KV cache is rotated automatically, and q8_0 KV is near-lossless on Qwen. The cost is 7-12% of decode speed on CUDA **[confirmed]**, https://github.com/ggml-org/llama.cpp/pull/21038. The environment variable to switch rotation off was renamed, so check the merged code before relying on it. Gemma is sensitive: q8_0 KV gives KLD 0.108-0.377 against 0.024-0.039 for Qwen **[confirmed]**, https://localbench.substack.com/p/kv-cache-quantization-benchmark.
- **KV pairs that a default CUDA build does not compile fall back to f16 with a warning** **[confirmed]**, https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md.
- **Hybrid attention changes the KV math.** In Qwen3.5/3.6 only one layer in four keeps a KV cache: about 20 KiB/token for the 35B-A3B and 32 KiB for the 3.5-4B, against 144 KiB for the classic Qwen3-4B **[confirmed]**, https://huggingface.co/Qwen/Qwen3.6-35B-A3B. Classic math over-reserves VRAM four to seven times.

### The rules Architect encodes (reasons shown on hover)

1. A small dense model that fits fully on the card uses Q6_K or Q8_0. The memory is spare and small models are the most sensitive to quantization. Drop to Q4_K_M only if speed is below target.
2. MoE experts held in RAM use Q4_K_M or IQ4_XS. Prefer K-quants over IQ3 on the CPU until measured otherwise.
3. Never go below UD-Q2_K_XL for any tier that calls tools.
4. KV type is chosen per model family and per build: Qwen q8_0, Gemma f16, router and draft f16. q4_0 only when the only alternative is not fitting at all, with a plain warning.
5. Context comes from real use: the 95th percentile of logged prompt sizes × 1.25, not the model maximum. On a 6 GB card, 1 GB of KV costs about 4-5 GPU layers of the 14B **[estimate]**.

### How a choice is made

For each tier, Architect builds a "quant ladder" from the files already on disk:

1. Drop the files that cannot fit.
2. Run a KLD pre-screen with `llama-perplexity --kl-divergence` against the best local file, using your own code and transcripts as the test text.
3. Run a speed probe.
4. Run a paired eval slice and count flips: tasks fixed or broken by the change, tested with exact McNemar.

The reason for pairing: with 109 tasks at about 80% pass, one run has a standard error of about 3.8 points **[estimate]**, so unpaired runs cannot tell neighbouring quants apart.

There is also a known bug: the fit always uses the quantized KV size, but the KV flags are passed only when flash attention is on and the layer count is above 0 **[code]**. CPU tiers therefore run f16 caches that were sized as q8_0.

The result is shown as one sentence, for example: "Q6_K: 3.5 GB, about 50 tok/s, 104/109. Q4_K_M: 2.7 GB, about 60 tok/s, 103/109. You lose one task for 20% more speed." Every number is labelled measured or estimate.

### How an unknown model is evaluated

A staged intake that uses only local files:

1. **Read the metadata** without loading the model: architecture, total and active parameters, quant, template, tokenizer hash, MTP tensors present. From that, predict fit and speed for each placement. Flag "community-modified" names (uncensored, abliterated, merge).
2. **Run a 60-second llama-bench** at low priority.
3. **Run a format smoke test**: 10 tool-call and edit prompts in the flow's real format, scored by the well-formed rate.
4. **Run a stratified 20-task eval slice**, paired against the current holder of the tier, with two seeds.
5. **Run a KLD check** if a higher-precision copy of the same model exists.

The verdict comes in plain words, for example "better than your current worker, at 52 tok/s", with Promote (undoable), Keep as alternate, and Ignore.

## 6. Harness and agent techniques, ranked by gain per effort

On Terminal-Bench, the choice of harness mattered about as much as the choice of model **[unverified]**: the harness research summary was cut off before its verification block. The numbers below are therefore marked unverified unless they are facts read from Architect's own code.

| # | Technique | Evidence | Architect today | Effort |
|---|---|---|---|---|
| 1 | **Lenient edit matching** (whitespace, indentation, fuzzy anchor, then ask) | Lenient patching cut edit errors 9x **[unverified]** | EDIT/SEARCH tolerates only trailing whitespace **[code]** (`arch_core.py` near line 700) | S |
| 2 | **Code outside JSON.** The tool call names the file, and the code goes in a fenced block after it | Code wrapped in JSON scored lower for every model tested **[unverified]** | `apply` carries code escaped inside a JSON string **[code]** | S |
| 3 | **Hide old tool output.** Keep the last 1-2 outputs in full and replace older ones with a one-line stub | Half the cost at the same solve rate **[unverified]** | Every observation (up to 4000 chars, 8 steps) is resent each step **[code]** | S |
| 4 | **Compaction at fixed size thresholds, never edits to earlier turns** | Hybrid DeltaNet models lose cache reuse when earlier turns are edited **[unverified]** | Not handled | S |
| 5 | **More samples checked by code, and a better pick of the winner** | 15.9% → 56% on SWE-bench Lite. Each verifier type alone stalls at 42-43%; a hybrid reached 51% with a 32B model **[unverified]** | Best-of-N keeps the first pass and is set to 1 on small and mid profiles **[code]** | M |
| 6 | **Blocking hooks that feed back to the model** (Claude Code pattern): a failing check returns its reason as the next observation | Pattern | Hooks exist; check that their output reaches the model | S |
| 7 | **Read-only explore sub-agent** that returns a 10-line summary, so the worker's context stays small | Pattern | Not present | M |
| 8 | **Checkpoints with rewind** for every step, not only per run | Pattern | Undo exists per write | M |
| 9 | **Skills that load only when needed** (SQL, migrations, CI) | Pattern | Skills exist | S |
| 10 | Self-repair, debate, multi-agent | At most +4.6 points on average for 2-4x the tokens **[unverified]** | Avoid as a default | — |

Data and math work belongs in the harness too.

- **SQL:** write 4-8 candidate queries, run each read-only, and vote on the results. The top of the BIRD leaderboard uses many-sample self-consistency, and 2-7B specialists score 68-74% **[unverified]**, https://bird-bench.github.io/.
- **Math:** the model writes Python or sympy checks that must agree before the done gate. Tools lift small MoE models toward the ceiling, for example AIME25 89.1 → 99.2 for Nemotron 3 Nano **[unverified]**.

## 7. Flows and templates

Every template is a flow (a YAML file under `flows/`) plus a starter repository plus the checks that decide "done". Each template card in the gallery shows what you get, the checks that must pass, the time it takes on this machine (measured after its first run), and which tier does the work.

| Template | Built on | Checks that decide "done" |
|---|---|---|
| **SaaS starter** (FastAPI or Flask + SQLite + auth stub + one CRUD resource) | build, test, secure | pytest, schema check, secret scanner, OpenAPI valid |
| **Add a feature to my app** | build, review | Existing tests stay green, new tests added, diff review |
| **Fix this bug** (paste an error) | bugfix | Failing test written first, then passes |
| **IT script** (PowerShell or Bash: inventory, cleanup, backup) | config, secure | Syntax parse, dry-run mode required, no destructive command without a flag |
| **CI pipeline** | cicd | YAML schema, local act-style dry run where available |
| **Data: CSV/SQL question** | new `sql.yaml` | Read-only execution, self-consistency vote, row count sanity |
| **Data cleaning notebook to script** | refactor, test | Output equality on the sample |
| **Math / derivation with checks** | new `math.yaml` | sympy or numeric check agrees, else "not sure" |
| **Review my repo** | review, secure | Report only, no writes |

Two new flows (`sql.yaml`, `math.yaml`), the template manifests and the gallery UI fit in one night. Each template ships with 2-3 eval tasks, so it is measured from day one.

## 8. UX and visual system

The rules you approved still hold:

- four places (Projects, Workspace, Models, Settings);
- one action per step;
- plain words first, raw names on hover;
- cards only for objects;

The CSP is `'self'` and there are no web fonts. Bundled fonts must therefore be served by `architect_hub.py` from a local `fonts/` folder (`font-src 'self'`). `data:` URIs would need a CSP change.

| Use | Font | Licence | Size |

## 9. The overnight plan

### How the night runs

Workstreams run in order, with parallel agents only inside a workstream, on separate files. Two rules hold throughout:

- the heavy-job lock is respected: one GPU job at a time, at low priority, and only on AC power;
- no downloads, no model removals, no role reassignments, no system settings.

Every workstream must pass:

- the existing selftest suite (known pre-existing security failures excepted, as noted in memory);
- `eval --quick` with no pass-rate drop beyond noise, using paired comparison;
